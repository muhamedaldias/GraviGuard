## 1. PROJECT UNDERSTANDING

GraviGuard is a **concept demonstrator** for a pump-protection idea: when suction
conditions erode the NPSH margin of a centrifugal pump, an elevated gravity tank plus a
modulating valve dynamically raises NPSH available — only when needed (README.md:3-9).
All plant data is synthetic, seeded and deterministic; the app explicitly disclaims being
a design/sizing tool (README.md:7-9, METHODOLOGY.md:7-11).

Physics domain (METHODOLOGY.md §1, E1–E13):
- **NPSHa** = (P_surface − P_v)/(ρg) + Δz − h_loss (+ velocity head at the flange) — E1.
- **NPSH3**: required NPSH at the 3 % head-drop point; margin ratio **R = NPSHa/NPSH3**,
  R = 1 by definition at 3 % drop; incipient cavitation well above 1 — E4.
- **Antoine** vapour pressure for water 1–100 °C with a 0.981 seawater factor — E3.
- **Suction losses** h_loss = (f·L/D + K_fittings + K_strainer(t))·V²/2g — E2.
- **Suction specific speed** Nss (US/metric), a design guideline, not a threshold — E5/E6.
- **HI 9.8 submergence** S ≥ D(1 + 2.3·Fr) against air-ingestion vortices — E7.
- **Water hammer**: Joukowsky ΔP = ρaΔV for closure faster than 2L/a, else slow-closure
  ΔH ≈ 2LΔV/(gT); safe stroke ≥ 10·2L/a — E8.
- **Tank autonomy** t_aut = V_usable/Q — the tank covers transients, not continuous duty — E9.
- Mechanism honesty: vapour cavitation vs recirculation vs air ingestion are distinct;
  GraviGuard only claims to fix NPSH-limited vapour cavitation (E11, ApplicabilityPage).

Audience: engineering stakeholders evaluating the concept (demo/video, bilingual EN/AR,
likely Saudi water-sector context — SWA mentioned only to disclaim its data,
METHODOLOGY.md:10-11). Product promise: an interactive, deterministic, honest simulation
with a 21-scenario test bench, A/B twin, controller lab, and methodology transparency.
The promise is largely delivered by the physics core; the UI layer currently undermines
it in several places (wrong chart axes, dead controls, broken tour — §5).

## 2. ARCHITECTURE MAP

(node environment, tests/**/*.test.ts, vite.config.ts:13-18). No router, no backend,
no ESLint/Prettier config, no CI config in repo.

- `src/sim/*` — pure TS physics core (no DOM). SimEngine (engine.ts) owns state, steps at
  dt = 0.01 s; modules: fluid, pump, network, valve, cavitation, sensors, controller,

  20 ms/frame compute cap, 20000-step cap, posts SimState snapshots. `client.ts` —
  main-thread wrapper. `hooks/sim.ts` — module-singleton SimClient bound to zustand.
- `src/state/store.ts` — zustand: prefs (lang/theme/units/digits/quality), page id,
  snapshot, rolling history (3600 samples, ≥0.1 s spacing), params, seed, scenario.
- `src/i18n/` — static en/ar JSON (316 keys each), parity enforced by tests/i18n.test.ts.
- `src/pages/` (16) + `src/components/` (5: Badges, PidSchematic, PumpCutaway, RadialGauge,
  StripChart/uPlot). Styles: tokens.css (dark/light industrial palette) + global.css.
- Scenario JSON schema: types.ts:301-354 (id/name/nameAr/description/descriptionAr/tags/
  duration/seed/mode OFF|ON|AB|MANUAL/params dotted-key overrides/timeline keyframes/
  assertions/expected). Pack: public/scenarios/ (21 files + index.json), generated by
  scripts/generate-scenarios.ts; CLI runner scripts/run-scenarios.ts.
- State management pattern: single global store + worker singleton; pages read snapshots
  via selectors; heavy A/B/comparison/MC runs execute SimEngine **on the main thread**
  (Twin.tsx:17-33, ControllerPage.tsx:31-54, ScenariosPage.tsx:34-40, sweep.ts) — the
  worker is used only by the live Simulator.

junction rule, tank inertia ODE, mass balance, autonomy, controller thresholds, sensor
